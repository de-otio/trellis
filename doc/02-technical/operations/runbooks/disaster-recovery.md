# Runbook: Disaster Recovery

## Overview

Trellis uses two categories of CDK stacks:

| Type | Stacks | RemovalPolicy | Can recreate? |
|------|--------|---------------|---------------|
| **Stateful** | Network, Data, Storage, Auth | RETAIN (prod) | No — contains durable data |
| **Stateless** | Api, Workers, Cdn, Monitoring, Agents | DESTROY | Yes — recreate freely |

Stateful resources (RDS, DynamoDB, S3 buckets, Cognito, ECR) are protected with `terminationProtection: true` in prod.

## S3 Bucket Recovery

S3 bucket names are **auto-generated by CloudFormation** (not hardcoded). This means:
- Stack replacement works without name collisions
- Bucket names are unique per deployment
- All consumers discover bucket names via SSM Parameter Store

### Find bucket names

```bash
STAGE=dev
aws ssm get-parameter --name /trellis/$STAGE/media-bucket-name --query Parameter.Value --output text
aws ssm get-parameter --name /trellis/$STAGE/web-bucket-name --query Parameter.Value --output text
aws ssm get-parameter --name /trellis/$STAGE/exports-bucket-name --query Parameter.Value --output text
```

### Media bucket — recover deleted objects

Media bucket has three layers of protection:

1. **Versioning** — deletes add a marker; original data is preserved for 30 days (noncurrent version expiration)
2. **AWS Backup** (prod only) — daily backups retained for 30 days, independent of the bucket's version history
3. **IAM least-privilege** — application roles only have `PutObject`/`GetObject`, not `DeleteObject`

#### Option A: Restore via versioning (fastest, for individual objects)

```bash
MEDIA_BUCKET=$(aws ssm get-parameter --name /trellis/$STAGE/media-bucket-name --query Parameter.Value --output text)

# List delete markers (recently deleted files)
aws s3api list-object-versions --bucket $MEDIA_BUCKET \
  --query "DeleteMarkers[?IsLatest==\`true\`].[Key,VersionId]" --output table

# Restore a specific object (remove its delete marker)
aws s3api delete-object --bucket $MEDIA_BUCKET \
  --key "originals/<sha256hash>" --version-id "<delete-marker-version-id>"
```

#### Option B: Restore via AWS Backup (for bulk/catastrophic recovery)

Use this when versioning is insufficient (e.g. versions were purged, or bulk restore needed).

```bash
# List available recovery points for the media bucket
aws backup list-recovery-points-by-backup-vault \
  --backup-vault-name <vault-name> \
  --query "RecoveryPoints[*].{Id:RecoveryPointArn,Created:CreationDate,Status:Status}" \
  --output table

# Start a restore job (restores to a new S3 bucket)
aws backup start-restore-job \
  --recovery-point-arn <recovery-point-arn> \
  --iam-role-arn <backup-role-arn> \
  --metadata '{"DestinationBucketName":"trellis-restore-temp","NewBucket":"true"}'

# Monitor restore progress
aws backup describe-restore-job --restore-job-id <job-id>
```

After the restore completes, sync the recovered objects back to the live bucket:
```bash
aws s3 sync s3://trellis-restore-temp/ s3://$MEDIA_BUCKET/
aws s3 rb s3://trellis-restore-temp --force
```

### Web bucket — restore previous deploy

See the [rollback runbook](./rollback.md#flutter-web-rollback) for web bucket version restoration.

### Exports bucket — no recovery needed

Exports bucket has a 7-day auto-expiration lifecycle. Objects are ephemeral GDPR exports and not recoverable after expiration. Users can re-request an export.

## RDS Database Recovery

### Automated backups

RDS automated backups are retained for 1 day (dev) / 30 days (prod).

```bash
# List available snapshots
aws rds describe-db-snapshots \
  --db-instance-identifier trellis-$STAGE-db \
  --query "DBSnapshots[*].{Id:DBSnapshotIdentifier,Created:SnapshotCreateTime,Status:Status}" \
  --output table
```

### Point-in-time recovery

RDS supports point-in-time recovery (PITR) to any second within the backup retention window:

```bash
# Restore to a new instance (does NOT overwrite the existing one)
aws rds restore-db-instance-to-point-in-time \
  --source-db-instance-identifier trellis-$STAGE-db \
  --target-db-instance-identifier trellis-$STAGE-db-restored \
  --restore-time "2026-03-27T10:00:00Z" \
  --db-instance-class db.t4g.micro

# After verification, swap the connection by updating SSM
aws ssm put-parameter --name /trellis/$STAGE/db-endpoint \
  --value "<new-endpoint>" --type String --overwrite
```

**Warning**: After swapping the endpoint, restart Fargate to pick up the new connection:
```bash
aws ecs update-service --cluster trellis-$STAGE --service trellis-$STAGE-api --force-new-deployment
```

## DynamoDB Recovery

DynamoDB single-table uses on-demand mode with point-in-time recovery (PITR) enabled.

```bash
# Check PITR status
aws dynamodb describe-continuous-backups --table-name $STAGE-trellis

# Restore to a new table
aws dynamodb restore-table-to-point-in-time \
  --source-table-name $STAGE-trellis \
  --target-table-name $STAGE-trellis-restored \
  --restore-date-time "2026-03-27T10:00:00Z"
```

Most DynamoDB data is ephemeral (rate limits, caches, sessions) and self-heals. The critical namespaces are:
- `fedify:key:*` — ActivityPub actor key pairs (loss = identity change for federated actors)
- `config:feature-toggles` — feature flag state

## Cognito Recovery

Cognito user pools cannot be restored from backup. Protection strategy:
- `terminationProtection: true` on Auth stack in prod
- `RemovalPolicy.RETAIN` prevents accidental deletion
- User data can be exported via Cognito API if migration is needed

## Full Stack Rebuild

If a stateless stack is destroyed, redeploy from the current code:

```bash
cd infra
npx cdk deploy "Trellis-$STAGE-Api" --context stage=$STAGE
npx cdk deploy "Trellis-$STAGE-Workers" --context stage=$STAGE
npx cdk deploy "Trellis-$STAGE-Cdn" --context stage=$STAGE
```

Stateless stacks read all dependencies from SSM, so they rebuild cleanly as long as stateful stacks are intact.

If a **stateful stack** is destroyed in prod, escalate immediately — this is a data loss event. See the incident response procedure in `scripts/incident/`.
